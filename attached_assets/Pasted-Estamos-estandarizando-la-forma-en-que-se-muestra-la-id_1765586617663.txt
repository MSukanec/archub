Estamos estandarizando la forma en que se muestra la identidad de una persona (usuario, miembro, contacto) en toda la aplicación.

Actualmente, el avatar + nombre se renderiza de formas distintas en tablas, modales, selects y vistas, lo cual genera inconsistencias.

Tu tarea es crear UN SOLO componente base reutilizable, con lógica y comportamiento estándar, siguiendo prácticas de SaaS de nivel profesional (Notion / Linear / Slack).

1️⃣ Crear componente base de identidad (NO contextual)

Crear un componente único, por ejemplo:

IdentityBadge


⚠️ Este componente:

NO debe conocer conceptos de negocio (roles, permisos, billing, etc.)

NO debe depender del lugar donde se use

NO debe asumir que es un “usuario” (también aplica a contactos)

2️⃣ Props mínimas y claras

El componente debe aceptar al menos:

name: string | null

avatarUrl?: string | null

size?: 'xs' | 'sm' | 'md' | 'lg' (default: md)

layout?: 'row' | 'column' (default: row)

showName?: boolean (default: true)

subLabel?: string | null (opcional)

interactive?: boolean (default: false)

className?: string

3️⃣ LÓGICA INTERNA OBLIGATORIA (muy importante)

El componente debe manejar internamente:

Avatar

Si hay avatarUrl → mostrar imagen

Si NO hay avatar → generar initials a partir del nombre

Si no hay nombre → fallback "?"

Avatar siempre circular

Nombre

Truncar nombres largos correctamente

Si showName = false, no renderizar texto

Accesibilidad

alt correcto en imágenes

roles semánticos si corresponde

4️⃣ MARCADO VISUAL TEMPORAL (CRÍTICO)

Para poder identificar visualmente dónde el componente ya está implementado y dónde no:

👉 Agregar un borde visible al avatar, usando el color de acento global del sistema.

Ejemplo conceptual:

borde 2px

color: var(--accent-color) o equivalente del tema

⚠️ Este borde es intencionalmente visible y debe:

estar presente SIEMPRE que se use IdentityBadge

permitir identificar rápidamente qué lugares ya usan el componente

⚠️ Documentar claramente que este borde es temporal y fácil de remover luego.

5️⃣ Comportamiento visual estándar

Alineación consistente

Espaciados internos uniformes

Tamaños proporcionales según size

Cursor pointer solo si interactive = true

6️⃣ Uso esperado (NO implementar automáticamente en todos lados)

NO refactorizar toda la app a ciegas.

En su lugar:

Reemplazar solo algunos usos claros (ej: una tabla o un modal)

Dejar el resto intacto

El objetivo es que el desarrollador (yo) pueda:

ver claramente dónde ya se usa el nuevo componente

detectar visualmente dónde todavía NO

7️⃣ NO tocar estos casos ahora

Sidebar avatar del usuario

Botón de perfil

Casos donde solo hay avatar sin nombre

Estos se resolverán más adelante.

8️⃣ Documentación obligatoria

Crear un archivo Markdown, por ejemplo:

docs/identity-badge.md


Que explique:

propósito del componente

props disponibles

lógica de fallback

por qué tiene borde visible

cómo detectar qué lugares ya están migrados

cómo remover el borde más adelante

9️⃣ Restricciones importantes

❌ No crear múltiples componentes similares
❌ No duplicar lógica en tablas o selects
❌ No hardcodear estilos por contexto
❌ No mezclar identidad con lógica de negocio

✅ Un solo componente
✅ Reutilizable
✅ Lógico
✅ Escalable

10️⃣ Objetivo final

Tener una representación de identidad coherente y profesional en toda la app, que permita:

consistencia visual

refactors globales simples

evolución futura (estado, rol, presence, etc.)
