**ASUNTO:** Implementación de Cron Job para Ejecución de Downgrades Programados.

**CONTEXTO:**
Los usuarios pueden programar un cambio a un plan inferior (downgrade) para el final de su ciclo de facturación actual. Esta intención se guarda en la columna `scheduled_downgrade_plan_id` de la tabla `organization_subscriptions`. Actualmente, cuando llega la fecha de expiración, el sistema no ejecuta esta acción automáticamente (GAP CRÍTICO).

**OBJETIVO TÉCNICO:**
Crear una nueva tarea programada (Cron Job) que se ejecute periódicamente para encontrar estas suscripciones vencidas y procesar el cambio de plan.

**REQUISITOS ESPECÍFICOS:**

**1. Nuevo Job (`server/cron/jobs/execute-scheduled-downgrades.ts`):**
* Este job debe ejecutarse con frecuencia, por ejemplo, **cada hora**.
* Debe usar el cliente Supabase con `service_role`.

**2. Lógica de Selección (Query):**
* Debe buscar en la tabla `organization_subscriptions` las filas que cumplan TRES condiciones:
    1.  `status = 'active'` (Aún la consideramos activa hasta que la procesemos).
    2.  `expires_at < NOW()` (Ya pasó su fecha de vencimiento).
    3.  `scheduled_downgrade_plan_id IS NOT NULL` (Tiene un downgrade pendiente).

**3. Lógica de Ejecución (Para cada suscripción encontrada):**
* **IMPORTANTE:** Debes reutilizar la lógica central de cambio de plan que ya existe en el sistema. Probablemente necesites refactorizar o adaptar la función `upgradeOrganizationPlan` (en `server/lib/handlers/checkout/shared/subscriptions.ts`) para que pueda ser llamada internamente por el sistema sin depender de un nuevo ID de pago externo. Quizás crear una función interna `internalSwitchPlan(orgId, newPlanId)`.
* **El proceso debe:**
    * Marcar la suscripción actual como `'expired'`.
    * Crear una *nueva* suscripción con el plan indicado en `scheduled_downgrade_plan_id`.
    * Actualizar el `plan_id` en la tabla principal `organizations`.
    * Limpiar el campo `scheduled_downgrade_plan_id` de la suscripción vieja para que no se procese de nuevo.

**4. Registro de Auditoría (Logs):**
* Por cada intento de downgrade, inserta un registro en la nueva tabla `public.system_job_logs`.
* Registra el `organization_id`, el tipo `'execute_downgrade'`, el resultado (`success` o `error`) y detalles útiles en el JSONB (ej: `{ "from_plan": "...", "to_plan": "..." }`).

**ENTREGABLES:**
* El nuevo archivo del job en `server/cron/jobs/`.
* La lógica interna necesaria para realizar el cambio de plan sin un nuevo pago.
* La integración del job en el index del cron para que se ejecute cada hora.
