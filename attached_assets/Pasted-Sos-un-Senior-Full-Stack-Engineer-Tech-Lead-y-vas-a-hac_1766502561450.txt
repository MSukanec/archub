Sos un Senior Full-Stack Engineer + Tech Lead y vas a hacer una AUDITORÍA 360° de un feature de Seencel ya lanzado en producción.

OBJETIVO
- Auditar y dejar “cerrado” el feature: {NOMBRE_DEL_FEATURE} (ej: “Mano de obra”).
- Resultado final: sin errores, consistente con la arquitectura actual, rápido, seguro (RLS), y documentado.
- NO quiero refactor masivo ni reescritura general del sistema: solo lo necesario para que este feature quede 100% sólido.

REGLAS DE SEGURIDAD (MUY IMPORTANTE)
1) No rompas compatibilidad: cualquier cambio debe ser incremental y verificable.
2) Antes de modificar archivos o SQL, entregame un “AUDIT REPORT” completo.
3) Solo después, entregame un “PLAN DE EJECUCIÓN” por pasos + checklist de validación.
4) Si hay riesgo de romper producción, proponé alternativa segura (feature flag / fallback / migración gradual).
5) No inventes tablas/columnas: si falta algo, marcá “FALTA” y pedí confirmación o proponé migración explícita.

CONTEXTO DE ARQUITECTURA (ASUMIR ESTO)
- Frontend: React + Vite + Tailwind (SPA), hooks, stores (Zustand), componentes reutilizables.
- Backend: Supabase (Postgres + Views + RLS + Functions/Triggers + Storage).
- La app tiene features en distintos niveles de madurez. Queremos estandarizar este feature al estándar “más avanzado” (ej: General Costs).
- Preferimos: Views en Supabase para joins repetidos y lecturas complejas (mejor que joins en front), queries claras, hooks consistentes, cero duplicación, y performance.

TAREAS DE AUDITORÍA (NO TE SALTEES NADA)
1) MAPA DEL FEATURE
- Dibujá el flujo de datos y pantallas: UI -> hooks -> queries -> views/tables -> RLS.
- Listá las rutas/archivos exactos involucrados.
- Listá endpoints / queries principales y sus responsabilidades.

2) AUDITORÍA DE BASE DE DATOS (Supabase)
- Verificá: tablas, tipos, relaciones, índices, constraints, defaults, not null, soft delete si aplica.
- Verificá si faltan VIEWS para lectura consolidada (evitar joins en el front).
- Chequeá coherencia de nombres y columnas con lo que consume el front.
- Verificá RLS:
  - SELECT / INSERT / UPDATE / DELETE según convención.
  - Políticas en mayúsculas y en español: “SUJETO > ACCIÓN > OBJETO > CONDICIÓN”.
  - Confirmá que no hay duplicaciones peligrosas ni huecos de seguridad.
- Output DB: “DB Findings” + “DB Fixes” (SQL exacto sugerido, separado por migraciones pequeñas).

3) AUDITORÍA DE FRONTEND
- Estructura del feature: archivos, separación de responsabilidades, consistencia con el patrón actual.
- Hooks:
  - que no haya duplicados
  - que no hagan joins pesados en el front si debería ser view
  - manejo de loading/error/empty states consistente
  - tipado/validaciones donde aplique
- Performance:
  - evitar re-fetch innecesario
  - cache y staleTime si usamos React Query (o patrón equivalente)
  - evitar renders innecesarios
- UI/UX:
  - estados vacíos, errores, permisos (si no puede ver/editar)
  - consistencia visual con la app
- Output FE: “FE Findings” + “FE Fixes” (por archivo, con cambios propuestos).

4) AUDITORÍA DE CALIDAD / ROBUSTEZ
- Manejo de errores real: logs, try/catch, supabase errors, mensajes al usuario.
- Validaciones: en front y DB (constraints).
- Concurrencia: updates que pisan datos, optimistic updates si aplica.
- Seguridad: nunca confiar en el front para reglas críticas.

5) RESULTADOS OBLIGATORIOS (ENTREGABLES)
ENTREGABLE 1: AUDIT REPORT (texto)
- Estado general: {verde/amarillo/rojo}
- Checklist de madurez (DB / RLS / Views / Hooks / UI / Performance / DX)
- Top 10 riesgos/bugs (con severidad: crítica/alta/media/baja)
- Lista completa de hallazgos (DB y FE) con evidencia (archivos/consultas/lineas si podés).

ENTREGABLE 2: PLAN DE EJECUCIÓN (paso a paso)
- Fase 0: backups y medidas anti-rotura
- Fase 1: DB (migraciones pequeñas) + verificación
- Fase 2: Front (refactors mínimos) + verificación
- Fase 3: Performance + limpieza
- Checklist final “Definition of Done” para declarar el feature terminado.

ENTREGABLE 3: CAMBIOS CONCRETOS
- SQL propuesto (migraciones pequeñas, ordenadas)
- Cambios por archivo (lista de archivos + qué cambia + snippet si aplica)
- Si algo requiere decisión, poné “DECISIÓN” con 2 alternativas y recomendación.

CONDICIÓN FINAL (“CERRADO”)
El feature se considera cerrado cuando:
- No hay errores en consola ni en runtime.
- DB tiene estructura correcta y lecturas principales por Views cuando corresponde.
- RLS consistente y segura.
- Hooks consistentes, sin duplicados y sin lógica redundante.
- UI completa (loading/error/empty/permisos) y consistente.
- Documentación corta del feature queda creada: “/docs/features/{feature}.md” con:
  - propósito
  - tablas/views
  - RLS resumen
  - hooks usados
  - flujo de datos
  - checklist de mantenimiento.
